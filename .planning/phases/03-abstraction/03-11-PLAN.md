<objective>
Close the F1 + F2 gaps surfaced by the 03-10 operator-witnessed SITL gate (see 03-10-SUMMARY.md):

- **F1 (regression, high severity):** Web UI velocity status bar is stuck at constructor defaults (`IDLE | Fwd 0.00 | Down 0.00 | Yaw 0.0`) because the Phase-3 controller→Robot signature migration (03-07 commit `7f602d2`) deleted the pre-Phase-3 `ui_state.update_velocity(...)` call site that lived inside `live_control_loop`. The replacement orchestrator (`run_robot_loop` in `robot_api/orchestrator.py`) has no `ui_state` parameter and never publishes mode+velocity to the UI. Operators in flight see a stale status bar even though the drone is actively moving — a situational-awareness blocker.
- **F2 (pre-existing, low severity):** `ctrl: bh=... factor=... filtered=...` at `hailo_drone_detection_manager.py:533` emits INFO every tick (~10 Hz) and was louder than expected during the gate run. Demote to DEBUG.

Purpose: restore operator situational awareness in flight (mandatory before Phase-3 closes — ABS-11 gate). Fold F2 in because both surfaced together and both belong to an "is the operator getting good telemetry?" cluster.

Output: orchestrator publishes a robot-agnostic `(forward, down, yawspeed, mode)` tuple to `ui_state` after each tick branch, with mode strings symmetric across drone and rover (AUTO/LOCKED/LOST/IDLE). UI status bar updates at ≥5 Hz during follow. New unit test pins the publish behavior. INFO log spam demoted to DEBUG. The MavsdkDroneAdapter remains UI-agnostic (axes-only contract preserved).

**Architectural decision (recorded in must_haves.truths and inline in the orchestrator):** publish the controller's PRE-smoothing `cmd` (matches pre-Phase-3 behavior) and do it AT THE ORCHESTRATOR LEVEL (NOT inside `MavsdkDroneAdapter.send_command/send_zero/on_target_lost`). Rationale:
1. Axes-only Capabilities contract — adapters must not know about UI knobs; ui_state is an orchestrator-layer concern.
2. Pre-Phase-3 behavior used the controller's pre-smoothing values; preserves operator's mental model.
3. Symmetric for the future Ros2RoverAdapter — Phase-4 rover wire-up gets UI telemetry for free without touching the rover adapter.

Three branches inside the tick loop (lines 72-89):
- `if detection is not None`: `cmd = controller.compute(...)` → `await robot.send_command(cmd, safety_ctx)` → publish AUTO/LOCKED + cmd values
- `elif lost_for < search_enter_delay_s`: hold last_cmd → `await robot.send_command(last_cmd, safety_ctx)` → publish IDLE (holding) with last_cmd values (or zeros — see decision below)
- `else`: `await robot.on_target_lost(last_detection)` → publish LOST with zeros (yaw-spin is adapter-internal; not exposed)
Finally block (line 93): `await robot.send_zero()` → publish IDLE with zeros (shutdown).

**Mode decision matrix (orchestrator-internal; expand inside run_robot_loop):**
| Branch | Mode | (forward, down, yawspeed) |
|---|---|---|
| detection present | "AUTO" or "LOCKED" (see below) | cmd.forward_m_s, cmd.down_m_s, cmd.yaw_rate |
| hold (within search_enter_delay_s) | "IDLE" | 0.0, 0.0, 0.0 |
| lost (past delay) | "LOST" | 0.0, 0.0, 0.0 |
| shutdown (finally) | "IDLE" | 0.0, 0.0, 0.0 |

**Why pre-smoothing (not adapter post-smoothing):**
Operator sees what the controller commanded (the controller's intent). The smoother is a per-axis EMA + slew cap inside the drone adapter — it's a drone-specific safety/comfort step. Publishing post-smoothed values would (a) require ui_state inside the adapter, breaking the axes-only contract; (b) lag one tick behind the controller's actual command; (c) be undefined for rover (no smoother). Pre-Phase-3 emitted pre-smoothing values from `live_control_loop` per the SUMMARY's "Pre-Phase-3 call site" line — this restores symmetric semantics across robot kinds.
