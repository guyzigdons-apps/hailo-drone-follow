<objective>
Close F5 (the failure mode operator observed during the 03-14 SITL re-gate):

> servers.follow_server | Detection ID 1 not found. Available: {45}

The 03-13 client-side resolver picked the right id from `detectionsRef.current`,
and 03-15 carried the resolved bbox.h in the body — but the operator still hit
404. Reason: the SSE→browser→click→HTTP round-trip has independent latency from
the pipeline→shared_state path. When the click arrives at the server, the
pipeline may have advanced PAST what the client knew at click time. No
client-only fix can win this race, because the client cannot know what the
server's "latest" will be when its HTTP request lands.

The fix is server-side, but PRINCIPLED (not the rejected `len==1` heuristic from
commit `72add07`): the client sends the bbox geometry of what the operator
visually clicked; the server matches that against its own atomic
`{id: bbox}` snapshot via IoU; the principled "best geometric overlap above
threshold wins" beats both client-only resolution (loses the race) and the
vetoed single-available heuristic (fires on the wrong target in multi-actor
scenes).

See `~/.claude/projects/-home-guyz-code-guyz-hailo-drone-follow/memory/feedback_click_to_follow_id_resolution.md` (revised 2026-05-19) for the locked
architectural rule: client renders + resolves; client sends full bbox geometry;
server does atomic id+bbox match; ui_state is NOT consulted in the recovery
path. The combination of all four layers is what closes the race.

**Architectural constraint (HARD):** `MavsdkDroneAdapter` and everything under
`robot_follow/robot_api/` MUST be untouched (axes-only contract). All edits
live in: state.py (data layer), the pipeline callback (producer), follow_server
(consumer), App.jsx (client). No adapter changes; no controller changes.

- All six in-scope callsites get `available_bboxes=filtered_tlwh_by_id` appended. The early-return at line 287 stays as-is (no bboxes to publish).

**Server** (`robot_follow/servers/follow_server.py`):
- `_read_bbox_h_from_body` → renamed to `_read_bbox_from_body`. Validates all four normalized floats. Returns `{x, y, w, h}` dict or `None`.
- New static `_iou(a, b)` helper: standard normalized-bbox IoU, returns 0.0 if union is 0.
- `do_POST /follow/<id>` body parsed ONCE (used for recovery + setpoint capture).
- Recovery branch: when `requested_id not in available_ids` AND `body_bbox is not None`, iterate `get_available_bboxes()` computing IoU; pick the highest. Threshold `0.3` — if any candidate clears it, lock that id; else 404.
- INFO log on recovery: `Stale detection ID 1 → bbox-matched 45 (IoU=0.85, available=[45])`.
- INFO log on 404: now reports `best bbox IoU 0.05 vs 1 candidate(s)` so the operator can see why recovery didn't fire.
- Success-path INFO log adds `id_source: requested|bbox-match`.

**Client** (`robot_follow/ui/src/App.jsx`):
- `handleFollow` POST body extends from `{bbox: {h}}` to `{bbox: {x, y, w, h}}` using `pick.bbox` verbatim.
- No other changes (detectionsRef + nearest-center resolver from 03-13 stay).

**IoU threshold (0.3) rationale:**
- A person walking between two ~100ms-apart frames overlaps themselves by IoU ≈ 0.85–0.95 (small translation, same scale).
- A bbox flicker (e.g., NMS edge case, detector noise) can drop IoU to ~0.5.
- A different person in the same general area can hit IoU ~0.1–0.2.
- 0.3 is the empirical floor for "this is the same visual target despite frame drift", well above noise.
- If multi-actor scenes need finer disambiguation, raise to 0.5 — but the multi-candidate test pins "pick the highest IoU" which already handles the common case.

**Headless caller compatibility:** `curl -X POST /follow/45` with no body still works for the happy path (id in available). On stale id with no body, server returns the existing strict 404. Recovery only fires when the body explicitly identifies the visual target.
