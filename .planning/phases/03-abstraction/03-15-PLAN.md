**Body schema for /follow/<id>:**

The client sends `Content-Type: application/json` with body `{ "bbox": { "h": <number> } }`. The server's tolerance ladder:
1. No `Content-Length` header OR `Content-Length: 0` → no body. Fall back to `_capture_bbox_for_id`.
2. Body present but not JSON → log warning, fall back.
3. JSON but no `bbox.h` field → fall back.
4. `bbox.h` present but not a finite number, or outside (0, 1] → log warning, fall back.
5. `bbox.h` valid → use it via `capture_bbox_setpoint_from_height(controller_config, h, source="CLICK")`. Log line says "from POST body" so the operator can audit.

The body schema is intentionally narrow — only `bbox.h` matters today, because the existing `target_bbox_height` setpoint is the only thing `_capture_bbox_for_id` writes. Wider geometry (x, y, w) is not used by the server and is not parsed.

**Why fall back at all (instead of failing the request):**
- curl users / scripted tests can hit `/follow/<id>` without a body. Backward compat.
- If the new client somehow sends bad JSON (browser cancellation mid-stream, proxy mangling), the fallback degrades to today's behavior ("n/a" log) rather than 4xx. The body-aware path is an enrichment, not a hard requirement.

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-03-15-01 | Denial of Service | malformed / oversized POST body | mitigate | Read EXACTLY `Content-Length` bytes (bounded by HTTP framing).
