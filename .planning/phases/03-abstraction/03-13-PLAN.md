Close F3 surfaced in the 03-12 operator-witnessed SITL re-run gate (see 03-12-SUMMARY.md § "F3 — `/follow/<id>` rejects clicks with stale ByteTracker IDs"):

- **F3 symptom (operator-observed):** during the `walk_across_then_approach` SITL run, the operator clicked the visible actor bbox in the web UI to lock-on. The console emitted `INFO | servers.follow_server | Detection ID 1 not found. Available: {45}` and the lock did NOT take. Root cause: React `onClick` handler closes over `det.id` at render time; if the SSE detection stream advances (ByteTracker loses + re-acquires the same person under a new track_id) between the React render and the click firing, the closure holds a STALE id that no longer matches any current detection.
- **Pre-existing**, NOT a Phase-3 regression — the strict server-side id check has existed since before the v1.1 rename.
- **Scope (per operator clarification):** the bbox has a **current id** at click time (whatever id the latest SSE frame assigned to the same visual target) and a **displayed id** (whatever React last rendered into the closure). The fix is to send the **current** id, not the displayed one, so the server can recognize what it's being asked about. The display stays as-is.

**Architectural decision (locks in the client-side fix):** the previous draft of this plan widened `follow_server.do_POST` to recover when `len(available_ids) == 1`. That approach was REJECTED — see `~/.claude/projects/-home-guyz-code-guyz-hailo-drone-follow/memory/feedback_click_to_follow_id_resolution.md`. Reasons:
1. The race lives on the client (React closure capture), so it should be fixed on the client.
2. The server should remain strict: id-not-in-available → 404. Weakening that contract hides the race instead of fixing it and adds a "guess the operator's intent" surface to the server.
3. The UI is the only party that knows what the operator visually targeted; resolution belongs there.

**Architectural constraint (HARD):** edits are CLIENT-LAYER ONLY. `robot_follow/servers/follow_server.py` MUST be untouched. `MavsdkDroneAdapter` and everything under `robot_follow/robot_api/` MUST be untouched. No Python file is modified. The axes-only Capabilities contract is preserved by construction.

Purpose: restore operator click-to-lock UX under the single-actor SITL flow (and any flow where ByteTracker re-IDs the same person between SSE render and click) so the ABS-11 SITL gate (re-run as plan 03-14) can pass. AUTO mode is unaffected (no operator clicks involved).

Output: `handleFollow` in `robot_follow/ui/src/App.jsx` reads the latest SSE detections via a `useRef` mirror at click time and resolves to the detection whose bbox center is nearest the clicked bbox center; that detection's id is what gets POSTed. The `onClick` payload changes from `det.id` to the whole `det` so the resolver has the clicked geometry. Vite build is verified clean.

**Resolution rule (position-based, simplest robust mechanism):**

At click time, `handleFollow(clickedDet)` reads `detectionsRef.current` (the latest SSE detection set) and picks the detection with the smallest squared distance between bbox centers vs the clicked detection. If `clickedDet.id` is still in the latest set, the nearest-center match will be that same detection (centers are byte-identical for an id that hasn't moved between render and click — the only re-ID race is when the upstream tracker re-IDs the bbox under a new id at roughly the same position). If `clickedDet.id` is gone (stale-id F3 case) but a new detection occupies a nearby center, the resolver returns that new id.

No distance threshold is applied — the operator-clarified intent is "the bbox the operator clicked has a current id; send that". In multi-person scenes, "nearest center" is the simplest mapping of "the bbox I clicked". A future plan can add an IoU-based resolver or a click-position-instead-of-bbox-center protocol if multi-actor scenes need finer disambiguation; out of scope for F3.

**No new failure modes introduced:**
- If `detectionsRef.current` is empty → resolver loops zero times; `pick` stays the original `clickedDet`; the existing 404 path on the server fires unchanged (same as today).
- If `clickedDet.id == null` → existing guard at the call site (`onClick={hasId ? ... : undefined}`) means `handleFollow` is never invoked for id-less detections; the resolver still gracefully short-circuits with an `if (pick.id == null) return;` guard at the end.
- If the resolver picks a different id than `clickedDet.id` → the server processes a real, current id. No additional log line is added on the client; if the operator wants to audit, the existing INFO line `Following ID 45 ...` (or similar) in the server log already records what got locked.

**Why not extract `resolveCurrentId` to a separate module:**
The function is ~10 lines and tightly coupled to React state (`detectionsRef.current`). Extracting it would require either passing the ref through (still tightly coupled) or making it a pure function and threading `latestDetections` from every caller — both adds friction with no payoff because there's no JS test framework. Keep it inline. The function is small enough that the operator gate provides sufficient validation.

      // React's onClick closure captures det.id at render time; if ByteTracker
      // re-IDed the same visual target between the render and the click firing,
      // that id is stale and the server returns 404 (F3 from 03-12-SUMMARY.md).
      // Pick the detection whose bbox center is nearest the clicked center.
      const latest = detectionsRef.current;
      const cx = clickedDet.bbox.x + clickedDet.bbox.w / 2;
      const cy = clickedDet.bbox.y + clickedDet.bbox.h / 2;
      let pick = clickedDet;
      let best = Infinity;
      for (const d of latest) {
        if (d.id == null) continue;
        const dx = (d.bbox.x + d.bbox.w / 2) - cx;
        const dy = (d.bbox.y + d.bbox.h / 2) - cy;
        const dist2 = dx * dx + dy * dy;
        if (dist2 < best) { best = dist2; pick = d; }
      }
      if (pick.id == null) return;
      try {
        const port = config?.follow_server_port || 8080;
        const host = window.location.hostname;
        await fetch(`http://${host}:${port}/follow/${pick.id}`, { method: "POST" });
      } catch {
        // ignore
