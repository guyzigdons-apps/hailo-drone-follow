Land RINT-02 per the locked Q1 decision: the rover adapter explicitly zeroes `twist.linear.x` when `safety_ctx.bbox_bottom_norm >= 0.85`, preserving yaw so the rover can still recenter. **The exact wire-level change** (per locked Q1):

In `robot_follow/robot_api/adapters/ros2_rover.py::send_command` (currently at `ros2_rover.py:112-124`), after the existing `twist.linear.x = cmd.forward_m_s` and `twist.angular.z = cmd.yaw_rate` lines, but BEFORE the `self._publisher.publish(twist)` call, add a single conditional:

```python
if (safety_ctx.bbox_bottom_norm is not None
        and safety_ctx.bbox_bottom_norm >= ROVER_BOTTOM_STOP_THRESHOLD):
    twist.linear.x = 0.0
```

`ROVER_BOTTOM_STOP_THRESHOLD = 0.85` is declared as a module-level NAMED CONSTANT at the top of the file. Per Phase 6 user decision: this MUST be a named constant, NOT a magic number embedded in `send_command`.

**Why this is the right shape** (Q1 locked decision):

- `safety_ctx.bbox_bottom_norm is not None`: defensive against any caller (e.g., `SafetyContext.lost()`) that leaves the field at its None default. The existing `if safety_ctx.target_lost: return` earlier in the method already covers the lost path; the None check is belt-and-braces.
- `>= ROVER_BOTTOM_STOP_THRESHOLD`: at 0.85 the person's bbox bottom is at 85% of frame height, i.e. the person occupies the lowest 15% of the frame. This is the "too close to the rover" signal — the rover should stop driving forward to avoid a collision.
- `twist.linear.x = 0.0` only: the yaw axis (`twist.angular.z = cmd.yaw_rate`) is intentionally PRESERVED so the rover can still rotate to recenter the target. If yaw were also zeroed, the rover would freeze entirely — wrong for the use case (the operator/auto-mode wants the rover to keep tracking the actor even when stationary).
- `cmd` is NOT mutated: `RobotCommand` is a value type emitted by the controller; mutating it after compute would create surprising upstream side effects. The override mutates only the `twist` object that's about to be published.

**Why the drone path is provably unaffected:**

- `MavsdkDroneAdapter.send_command` lives in `mavsdk_drone.py`. This plan does not touch that file (architectural lock).
- The drone adapter reads `safety_ctx.bbox_bottom_normalized` (the legacy field) for its retreat-from-tilt logic. The new `bbox_bottom_norm` field is populated by `SafetyContext.from_detection` (06-01) but the drone adapter NEVER reads it. The drone-path safety contract is untouched.
- Plan 06-01 added `bbox_bottom_norm` as `Optional[float] = None` appended to the dataclass — the field's presence does not change `bbox_bottom_normalized`'s wire path for any existing reader.

**Capabilities axes-only contract** (ABS-05 lock + `feedback_robot_abstraction_axes_only.md`):

This plan does NOT add a `bottom_edge_policy` flag to `Capabilities`. The threshold is a rover-specific behavior that lives entirely inside the rover adapter. A future drone with no tilt physics would need its own adapter-specific bottom-edge logic; a `bottom_edge_policy` flag in Capabilities would smuggle robot knowledge back into the controller, defeating the abstraction.
