**The five-line change** (per RESEARCH § RINT-03):

1. `create_app` signature gains `controller_config: Optional['ControllerConfig'] = None` (None default falls back to `ControllerConfig()` stock — preserves legacy callers).
2. Inside `create_app`, BEFORE the `create_tracker` call, normalize: `_cfg = controller_config if controller_config is not None else ControllerConfig()`.
3. Replace the four numeric literals in the `create_tracker(...)` call with reads from `_cfg.bytetracker_*`.
4. `robot_follow_app.py` at the `create_app(...)` invocation (currently line 431) passes `controller_config=ControllerConfig.from_args(pre_args)` as a new keyword argument. This is **Path A** wiring per RESEARCH: a first-pass ControllerConfig is built from pre-parsed args BEFORE `create_app` runs; the EXISTING line-448 `ControllerConfig.from_args(args)` call STAYS UNCHANGED and continues to be the source of truth for the rest of the app.
5. New test file `test_bytetracker_config.py` with 4 tests locks the wiring at the unit level.

**Why this is one plan, not split:**

The 5 changes are tightly coupled — extracting them across multiple plans would leave an intermediate state where the tracker reads stale literals while the config has fresh values (an asymmetric drift mode). Atomic landing keeps every intermediate `git bisect` point correct: at HEAD of this plan, `--robot drone` works exactly as it did pre-Phase-6 (drone defaults preserved byte-identically), AND `--robot rover --config configs/rover_simulation.json` exercises the override path.

**The drone-defaults regression guard (RINT-03 hard contract):**

`ControllerConfig()` (no args, no JSON) MUST produce the four legacy literal values `(0.4, 90, 0.5, 30)`. Plan 06-01 added the fields with these exact defaults. This plan inherits that contract and asserts it from a fresh angle: not just "the dataclass has these defaults" but "the create_tracker mock receives these kwargs when controller_config is the stock ControllerConfig()".

**Path A wiring vs Path B (RESEARCH § File-by-File):**

- **Path A (this plan):** Build `ControllerConfig.from_args(pre_args)` BEFORE `create_app` to seed the tracker; keep the existing line-448 `ControllerConfig.from_args(args)` call for the rest of the app. Two ControllerConfig objects briefly coexist; both honor `--config` because `--config` is registered on the pre-parser too (verified next).
- **Path B (deferred):** Hoist the entire `ControllerConfig.from_args(args)` call before `create_app` by widening the pre-parser to include every controller flag. Bigger refactor; deferred to a follow-up because the tracker init is the ONLY consumer this plan cares about, and tracker init reads only 4 fields.

**The Pitfall A guard** (RESEARCH § Common pitfalls): the two `from_args` calls must agree on the four `bytetracker_*` values. This is true IF (a) `--config` is on the pre-parser, AND (b) the operator doesn't pass `--bytetracker-*` flags on the CLI (we don't register them — RESEARCH § File-by-File recommendation). Both conditions are checked by the test in Task 3.
